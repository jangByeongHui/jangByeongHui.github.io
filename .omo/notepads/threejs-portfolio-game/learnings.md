- **Root cause**: `main.js`'s reduced-motion branch (from Todo 9) scheduled exactly one `requestAnimationFrame` render at boot and never again. `interactions.js`'s `flyToNode()` snaps `camera.position`/`controls.target` INSTANTLY under reduced motion (no tween) and `scene.js`'s resize listener updates `camera.aspect`/repaints the background gradient — both are real state changes that were never followed by a new render, so the DOM (info panel/HUD) updated correctly but the canvas visually froze on the boot-time frame forever.

Each trigger produces exactly one additional one-off frame — none of them re-schedule themselves, so the "no continuous loop under reduced motion" invariant (Todo 11's `rafCalls === 1` bar) still holds, just generalized to "no additional idle growth between discrete events" rather than "always exactly 1 forever."
- **Event-ordering correctness (non-obvious, worth re-reading if this code is touched again)**: `interactions.js`'s `onPointerUp` does `window.dispatchEvent(new CustomEvent('data-orbit:node-select', ...))` THEN synchronously calls `flyToNode(node)` right after — meaning our `data-orbit:node-select` listener actually runs (synchronously, as part of `dispatchEvent`) BEFORE the camera snap happens. This is fine specifically BECAUSE our listener only calls `requestAnimationFrame(...)`, which is inherently asynchronous (fires on the next paint) — by the time the scheduled callback actually executes, `flyToNode()` has already completed in the same synchronous call stack. If a future change ever made the listener render synchronously/immediately instead of via `rAF`, it would capture the STALE pre-snap camera position — the `rAF` indirection isn't just style, it's load-bearing for correctness here.
- **Cross-module resize-listener ordering (also load-bearing)**: `main.js`'s new `resize` listener is registered AFTER `initScene()` returns, and `scene.js` registers its OWN `resize` listener earlier, inside `initScene()` itself. Native `addEventListener` calls on the same target/event fire in registration order, so `scene.js`'s aspect/background update always completes before `main.js`'s listener schedules the repaint — no explicit event-detail/callback plumbing needed between the two modules, just relying on this ordering guarantee. Documented here so nobody "cleans up" by moving `main.js`'s listener registration earlier.
